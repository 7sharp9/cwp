### Design choices recorded in the task file

1. **Selected-client compile: deferred to P4.** The Godot project is C#, not in
   the slnx, and needs the Godot .NET SDK and a pinned Godot version — a CI
   toolchain of its own — to guard code that does not change during P3. The
   first P4 client task (B-024 / B-025) adds the client-compile,
   content-validation, and package-smoke jobs when there is client code for
   them to protect. Recorded as a deliberate deferral in the workflow's top
   comment and the B-048 row.
2. **Dependency locking: rely on the existing exact-version pins + `global.json`.**
   `docs/09` section 6 says "locked **or** pinned"; pinned is satisfied, and a
   cold-cache CI restore is itself the check that the pins resolve. Lockfiles
   add transitive pinning and restore-hash verification but are a committed
   source/config change (a `packages.lock.json` per project,
   `<RestorePackagesWithLockFile>`, an ongoing regeneration obligation) — an
   implementation task, not this CI-plumbing task. Flagged as a separate small
   task to revisit only if R-016 materialises; **not** given its own backlog
   number here.
3. **Runner OS: `windows-latest`.** CI must *reproduce* the committed hashes,
   not compute different ones, so it runs in the environment they were pinned
   in. `ubuntu-latest` would test a cross-platform determinism claim the
   project explicitly disclaims (`docs/09` section 3): a chance match would be
   unearned evidence, a mismatch would be a day-one red build forcing a per-OS
   hash-table format change (`Corpus.renderTable`, the `<name>.md` grammar,
   `Corpus.parseTable`) well outside this task. Linux / cross-platform CI stays
   an ADR-gated future decision. Because CI now depends on the
   single-environment pinning, the task adds a one-line Windows-x64 / .NET
   `10.0.303` annotation to `content/replays/CORPUS.md`,
   `content/fixtures/SPIKE-FIXTURE.md`, and the `docs/12` "Shared fixture"
   block — the only content/doc change, and it adds no new claim.
4. **`bench/`: built by the solution build, never executed.**
   `bench/CommandoWar.Benchmarks` is in the slnx with `TreatWarningsAsErrors`,
   so `dotnet build CommandoWar.slnx -c Release` already builds it and already
   fails on benchmark-code bit-rot, at zero extra cost. CI runs no benchmark
   (`docs/09` sections 2.8 and 5.6 — not a test oracle). This needs no special
   handling, only the absence of a `dotnet run --project bench/...` step.
5. **Genuinely a small implementation task.** Implementing it produces one new
   `.github/workflows/ci.yml`, three one-line doc annotations, and control-doc
   updates — no source, no `.fsproj`, no test, no hash. Size `S`, smaller than
   TASK-021. This drafting step produces only the task file plus backlog/ledger
   rows, matching the TASK-021 / TASK-022 draft precedent.

### Workflow shape specified for the implementer

Single file `.github/workflows/ci.yml`, one job, `runs-on: windows-latest`,
`permissions: contents: read`, `concurrency` keyed on the ref. Triggers: `push`
(any branch) and `pull_request` into `main`. Steps: SHA-pinned
`actions/checkout` and `actions/setup-dotnet` (`global-json-file: global.json`);
`dotnet restore CommandoWar.slnx`;
`dotnet build CommandoWar.slnx -c Release --no-restore`;
`dotnet test CommandoWar.slnx -c Release --no-build`;
`dotnet run --project src/CommandoWar.Headless -c Release --no-build -- corpus`
(fails the job on divergence);
`dotnet run --project src/CommandoWar.Headless -c Release --no-build -- fixture`
(smoke); `git diff --exit-code` (working tree unchanged). Optional hardening: a
NuGet cache keyed on the `.fsproj` files + `global.json` (no lockfile to key
on), and a `-- corpus --regenerate` + `git diff --exit-code content/replays`
idempotence check.
