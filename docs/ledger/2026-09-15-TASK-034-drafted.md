### Why this task, in this shape

TASK-033's acceptance (this session, immediately prior) left B-021 partial
and named B-022 (enemy doctrine) and B-023 (canonical refusal sequence) as
the next unblocked-or-nearly-unblocked candidates. B-022's dependencies
(B-015/TASK-026, B-019/TASK-031) are both `done`, so it is fully unblocked;
B-023 additionally needs B-021's remaining triggers and all of B-022, so it
is not yet ready to draft.

Read before drafting: `docs/05_COMMAND_AND_AGENT_AI.md` section 3 (squad
tactical picture) and section 12 (Enemy AI, the six-bullet doctrine list);
`docs/09_TEST_STRATEGY.md` section 8 ("enemy does not target an unobserved
player position", listed "partially realised"); `docs/11_BACKLOG.md` B-022's
row; `src/CommandoWar.Sim/{Domain.fs, Perception.fs, Simulation.fs,
Canonical.fs, Diagnostics.fs}` to establish what already exists versus what
this task would add.

Findings that shaped the cut:

- `docs/05` section 12 lists six doctrine bullets. Two are already real
  without this task: "hold assigned area" (a `Hostile` agent with no `Order`
  never moves — true by omission) and "engage visible targets"
  (`Simulation.combat`, TASK-031, is symmetric by construction). Three need
  systems that do not exist: "suppress likely routes" (a `Suppress` order,
  B-030), "seek cover under pressure" (the first autonomous-movement
  decision for an unordered agent — no design exists), "fall back under a
  scenario condition" (authored conditions + `Withdraw` semantics,
  B-030-adjacent).
- The remaining bullet, "observe and report", is genuinely unbuilt for the
  Hostile side: `Simulation.tacticalKnowledge` filters to
  `s.Agents |> Array.filter (fun a -> a.Side = Friendly)` before calling
  `Perception.mergeKnowledge` — the only place TASK-026's otherwise
  side-agnostic pure function is constrained to one side.
- `docs/09` section 8's "enemy does not target an unobserved player
  position" criterion, read closely, is **already true** mechanically:
  `Simulation.combat` draws shooter candidates only from
  `shooter.VisibleContacts` (TASK-031 Decision A, the R-023 "same
  observation contract" mitigation) — same-tick real-time visibility,
  strictly tighter than anything a stale-tolerant tactical-knowledge store
  could provide. The doc's "partially realised ... needs the hostile squad
  picture" framing conflates the targeting half (already true) with the
  observe-and-report half (not yet true); this task splits them and proves
  the former rather than building anything for it.

### Scope decision confirmed with Dave before drafting

Asked directly (`AskUserQuestion`) how much of the six-bullet doctrine to
build now, given the task is sized `M` and `docs/05` section 12 itself warns
"do not build a symmetric enemy commander planner before the player command
loop works." Dave chose the narrowest of three options: tactical picture
(new `WorldState.HostileTacticalKnowledge`) plus the observed-only-targeting
proof only, matching the TASK-032/033 narrow-cut precedent. The other two
options considered — adding a seek-adjacent-cover reaction to
`SuppressionBand`, or the full six-bullet doctrine including a new
`Suppress` order and scripted fallback — were both rejected as materially
larger than `M` and, for the full-doctrine option, in direct tension with
the "do not build a planner yet" guidance. Recorded as Decision A in the
task file.

### Design choices recorded in the task file (proposed, not yet confirmed line-by-line)

1. **New `WorldState.HostileTacticalKnowledge: Contact[]`, built by calling
   the existing `Perception.mergeKnowledge` a second time** (Decision B) —
   no change to `Perception.fs` itself; `Simulation.tacticalKnowledge` gains
   a second filtered call. `ContactObserved` already fires symmetrically for
   both sides (unconsumed until now); the new store's `ContactExpired`
   reuses the existing event shape.
2. **New `Overlay.HostileKnownContact` diagnostic case, not a reuse of
   `Overlay.KnownContact`** (Decision C) — the `AgentStress`/
   `AgentSuppression` precedent, so the two pictures stay visually
   distinguishable in a golden render.
3. **`Canonical.FormatVersion` 6 -> 7, full re-pin, not behaviour-neutral**
   (Decision D) — unlike TASK-026's original bump (no hostiles existed yet),
   `open-engagement`, `perception-contact`, and `exposed-approach` will
   legitimately gain new non-zero `HostileTacticalKnowledge` values. No new
   corpus entry needed.
4. **The "does not target an unobserved position" criterion is proven, not
   built** (Decision E) — one new/extended `SimulationTests` fact, plus a
   `docs/09` section 8 wording correction from "partially realised" to
   "fully realised" for the targeting half specifically.
5. **No new event type, no new corpus entry, no ADR** (Decision F) — the
   existing ADR-0002 amendment already governs a canonical-field addition
   like this one.

### Sizing

`M`. One new canonical field reusing an existing pure function, one new
diagnostic overlay case, a `FormatVersion` bump with a full (partially
non-behaviour-neutral) re-pin, and one new proof fact — comparable in shape
to TASK-032/033, smaller than a task that touched `Combat.fs` or added an
order type.
