### Why this task, in this shape

`docs/08_ROADMAP_AND_GATES.md` section 6 makes B-044 mandatory before G3
(added by the 2026-09-06 TASK-020 revision). TASK-020 deferred issue-tick
semantics because they were *semantically undefined*, not merely
unimplemented. Verified against source before drafting:

- `src/CommandoWar.Sim/Commands.fs`: `PlayerCommand.IssueTick: int64` is
  carried; its doc comment says "its semantics are unresolved ... backlog
  B-044, mandatory before G3".
- `src/CommandoWar.Sim/Simulation.fs` `commandIntake`: never reads
  `cmd.IssueTick`. `step` sorts the batch by `c.Id` only.
- `src/CommandoWar.Sim/Replay.fs`: `RecordedCommand.Tick` is "the tick whose
  command-intake phase consumes this command"; `Replay.run` filters
  `Array.filter (fun c -> c.Tick = tick)`; `Replay.validate` checks
  `(Tick, Sequence)` monotonicity and `c.Tick` in `[1, TickCount]` but **not**
  `CommandId` uniqueness.
- `src/CommandoWar.Headless/CommandLogFile.fs` `parse`: passes the one
  `.cwlog` tick token as `RecordedCommand.Tick` *and* as `Command.moveTo`'s
  `issueTick` argument — the two concepts are forced equal only by this call
  site.
- `src/CommandoWar.Sim/Canonical.fs`: `encode` takes `WorldState`;
  `PlayerCommand` / `RecordedCommand` are not encoded, so a field rename or a
  new rejection case moves no hash and `Canonical.FormatVersion` (2) does not
  change.

### Design recorded in the task file (recommended resolutions)

- **Decision 1 — two concepts, separated.** `IssuedAtTick` (rename of
  `PlayerCommand.IssueTick`) = issue-time provenance and a future appraisal
  input, carried in the envelope. `SubmitAtTick` (rename of
  `RecordedCommand.Tick`) = the caller-owned delivery/scheduling tick.
  Independent. Renaming both is recommended; renaming only
  `PlayerCommand.IssueTick` (with a clarifying doc comment on
  `RecordedCommand.Tick`) is allowed if the `Replay.fs` fan-out threatens the
  size; renaming neither is not.
- **Decision 2 — `IssuedAtTick` eligibility.** `commandIntake` rejects a
  command whose `IssuedAtTick` is after the running tick (`IssuedInFuture`)
  and one that is negative. A whole-command check, ordered with
  `EmptyRecipients` / `DuplicateRecipient` / `TargetOutOfBounds`.
- **Decision 3 — no staleness horizon.** A long-delayed command is accepted;
  whether to follow an outdated order is appraisal's judgment (B-017), not a
  validation constant. Recorded as a decision, flagged for B-016 / B-017.
- **Decision 4 — replay tick and issue tick independent.** The legacy
  `.cwlog` collapses both to its one field (issued-on-the-tick-it-is-
  delivered); the format that carries them separately is TASK-025 / B-045.
- **Decision 5 — command identity is not authoritative state.** `CommandId`
  stays a batch-local dedup key plus a **replay-log** uniqueness invariant
  (`DuplicateCommandIdInLog` in `Replay.validate`). No `WorldState` field, no
  cross-tick set in `commandIntake` — that would be unbounded per-tick state
  (`docs/04` section 19) for a guarantee the replay layer already gives.
  Consequence: `Canonical.FormatVersion` does not move.
- **Decision 6 — no bump, no hash re-pin, no ADR.** The `.cwlog` collapse
  keeps `IssuedAtTick == SubmitAtTick == tick` for every committed entry and
  `IssuedAtTick <= tick` always holds, so no existing command is newly
  rejected. `docs/08` section 6 already lists B-044.

### Sizing

`S–M`. The core is a field rename plus one or two validation branches plus a
replay-log check. The `RecordedCommand.Tick -> SubmitAtTick` rename fans out
across `Replay.fs` (`forTick`, `CommandLog.create`, `validate`, `run`),
`CommandLogFile.fs`, and `ReplayTests.fs`; if that proves noisy the implementer
may keep `RecordedCommand.Tick` and only rename the `PlayerCommand` field.
No `Canonical.FormatVersion` bump, no hash re-pin.
