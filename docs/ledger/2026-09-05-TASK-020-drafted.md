### Why this task, in this shape

Recommended as the first P3 unit of work once G2 passed (see the
`2026-09-05-G2-gate-decision.md` entry): B-014's only dependency, B-011
(movement), is done, and it unblocks the P3 appraisal/commitment chain
(B-017, B-018). Inspecting `src/CommandoWar.Sim/Commands.fs` before drafting
(`AGENTS.md` "read before editing") found the task's scope already named in
its own doc comment: "Recipients beyond a single agent, urgency and risk
tolerance are deferred to the command-validation task (backlog B-014)." The
task file's Central decisions section commits to a design that keeps every
existing single-recipient call site, `.cwlog` file, and pinned hash
untouched: `PlayerCommand.Recipients: AgentId list` generalises the single
`Agent` field, but `Command.moveTo` keeps its existing signature and default
`Urgency`/`RiskTolerance`; a new `Command.moveToMany` carries the
multi-recipient / non-default case. One `CommandAccepted`/`CommandRejected`
event per (command, recipient) pair, not per command, so every existing
one-recipient scenario emits the exact event sequence it always did.

`docs/04_SIMULATION_SPEC.md` section 12.1's "reject malformed, unauthorised,
... or duplicate commands" is answered narrowly: `EmptyRecipients`
(malformed), `UnauthorisedRecipient` (a `Hostile`-side recipient — the only
sense "authorisation" has in a one-player, all-friendlies vertical slice,
with no issuer-identity model invented), and `DuplicateCommandId` scoped to
the same tick's incoming batch only (cross-tick tracking would need
unbounded persistent state with no evidenced need). Issue-tick
eligibility/scheduling is explicitly left out: the `Commands.fs` comment
naming it as unenforced attributes no owning task, unlike the
recipients/urgency/risk-tolerance comment that names B-014 directly.
