### Why this change

The standing review would not accept TASK-020 as written and named six specific
weaknesses. TASK-020 is `ready` but not `active`, so the fix is to the task file,
not to an implementation. Each point was checked against the source before
editing:

1. **Objective overclaimed.** It said the task lands the section 13 envelope
   "in full" (ID, issuer, recipients, issue tick, urgency, risk tolerance) while
   its own body excludes issuer identity and issue-tick eligibility. Reworded to
   a **partial** envelope: multi-recipient addressing + inert urgency/risk +
   current-scope intake validation. The completion record must not claim
   section 13 is complete.

2. **Duplicate recipients were accepted.** The old decision let
   `Recipients = [a; a]` through as "idempotent". Changed to reject the whole
   command `DuplicateRecipient of AgentId`: a repeated id would emit duplicate
   `CommandAccepted` events, inflate any command-workload telemetry, and make a
   later per-agent appraisal / action-cost pass (B-017/B-018) run twice for one
   agent. The caller gets evidence it built an invalid envelope.

3. **"First duplicate command wins" was batch-order-dependent.** Verified:
   `Simulation.step` sorts the batch with `commands |> Array.toList |>
   List.sortBy (fun c -> c.Id)`, and `List.sortBy` is a stable sort, so equal
   ids keep caller order - a "process the first, reject the rest" rule lets a
   caller change the authoritative result by reordering an invalid batch.
   Changed to: any `CommandId` appearing more than once rejects **every**
   command in that group (`DuplicateCommandId`), none processed, one
   `CommandRejected` per command in the group. Order-independent.

4. **`IssueTick` was semantically undefined, deferred with "reopen if
   evidence requires".** Verified: `RecordedCommand.Tick` (replay submit tick)
   and `PlayerCommand.IssueTick` are two concepts, and
   `CommandLogFile.parse` passes the same value to both. Kept out of TASK-020,
   but the deferral is now a **named mandatory follow-up, B-044**, due before
   G3, that must settle authored-vs-submission-vs-acceptance time, future/stale
   command handling, replay-tick vs issue-tick matching, and whether command
   scheduling/identity is authoritative state (which also bounds the cross-tick
   duplicate-id question).

5. **`.cwlog` can no longer represent the command model.** After this task,
   multi-recipient addressing / `Urgency` / `RiskTolerance` exist in the type
   and not in the `<tick> <agentId> move <x> <y>` grammar. The task file now
   explicitly designates `.cwlog` a **legacy fixture-script format, not the
   production replay-command format**, and the real serialisation decision is a
   **named mandatory follow-up, B-045**, due before G3 (whose evidence requires
   replay to reproduce the complete decision trace).

6. **Per-command agent-array copy.** Verified: `commandIntake` does
   `Array.copy s.Agents` inside its `for cmd in commands` loop, and
   `content/benchmarks/BASELINE.md` records this as the first measured hot spot
   (50-command tick = 50 copies of a 50-element array, ~86 KB/tick, O(n^2)). The
   task now requires one `Array.copy` + one `AgentId -> index` lookup for the
   whole batch (agent identity and array order are stable within command intake).

Confirmed the task's own no-format-bump claim: `Canonical.encode` takes only
`WorldState`; `PlayerCommand` is not encoded, so `Canonical.FormatVersion` (2)
does not move.
